# USB 音频偶发 DMA 重启排查（2026-10-31）

## 已有证据

USB ISO OUT 中断接收 + SRAM 八包队列已解决多数丢包，但旧固件长时间日志
仍出现 TX DMA 重启。此次读取的日志片段包含 644 个五秒统计窗口、51 条
`TX DMA underrun`，部分窗口 USB 收满 5000 包仍重启，所以不能归为 USB
未供数或音频存放 PSRAM。TX 缓冲为内部 SRAM，4096 字节 / 64 ms。

## 官方参考与推断

- [Espressif P4 Memory Synchronization](https://docs.espressif.com/projects/esp-idf/en/latest/esp32p4/api-reference/system/mm_sync.html)：
  内部内存和外部 PSRAM 都可能经 CPU 缓存访问；DMA 绕过缓存，旧缓存写回
  会覆盖 DMA 更新。缓存同步必须考虑整个缓存行，而不仅是逻辑对象。
- [Espressif I2S 驱动](https://github.com/espressif/esp-idf/blob/master/components/esp_driver_i2s/i2s_common.c)：
  I2S 的 DMA 缓冲按约束对齐，并在 CPU/DMA 交接处同步缓存；链表通过指针
  连接。该源码仅用于参考，本项目不引入 C 实现。
- [esp-hal DMA 实现](https://github.com/esp-rs/esp-hal/blob/main/esp-hal/src/dma/buffers/mod.rs)：
  本地 1.2.0 的 streaming buffer 会 invalidate 描述符数组，修改已消费描述符
  及旧尾节点，再 writeback。DMA 此时仍会更新其他描述符。

本地 P4 `DmaDescriptor` 原为三个 32 位字、8 字节对齐，结构大小 16 字节，
一条内部 SRAM L1 DCache 的 64 字节缓存行容纳四个描述符。CPU 回收一个
描述符时把该缓存行标脏，随后 DMA 更新邻接描述符，CPU 再写回整行就可能
覆盖邻接描述符的新 owner/状态。这是根据源码与官方缓存模型得到的根因假设，
不能仅凭原理分析声称硬件问题已经解决。

## 单变量修改

仅在 P4 将 `DmaDescriptor` 的对齐和大小设为 64 字节，隔离每个描述符。
三个硬件字段偏移仍为 0、4、8，链表通过 next 指针寻址，不要求节点紧密排列。
增加编译期断言验证这些布局约束。其他芯片保持原有布局；不增大音频数据缓冲，
不暂停显示，也不通过关闭无线来掩盖问题。

TX/RX 各约 32 个描述符，内部 SRAM 描述符开销合计增加约 3 KiB。
全部二进制 release 编译通过，VIA 四层读取通过。仅改描述符布局的版本已观察
220 秒（44 个完整五秒窗口），DMA 重启/队列丢弃均为零，包含持续切页、按键和 Wi-Fi 扫描。
用户反馈“音频没卡，但是触摸卡的很”。仍有少量补零，提示原 4 ms 弹性队列
在复合负载最长 3–5 ms 的调度延迟下可能余量不足。

## 后续应用层优化

- 桌面复合程序 USB PCM 目标水位由 64 采样（4 ms）改为 128（8 ms），
  队列总容量仍为 256，DMA 数据环仍为 4096 字节。独立音频例程水位不变。
- 先试用 64 行静态 SRAM 条带，全屏绘制仅从约 220 ms 降至 190 ms，用户
  仍反馈慢。随后采用 32 行静态条带与脏行区间：密码输入只重画密码框；
  键盘高亮只重画变化按键所在行；跨页仍全屏。每个物理缓冲分别保存已绘 UI
  状态，按实际后台缓冲差异更新，避免交替翻页后恢复旧高亮。保留原帧边界等待。
- 这两项是在描述符单变量验证后加入，避免把降低 DMA 重启错误归因于扩大缓冲。

最终组合版已烧录并通过用户交互确认，不将有限时间零错误等同于永远不会断音。

触摸优化后用户确认“没问题”。实测按键局部绘制约 41–44 ms、含等待总计
77–86 ms；后台帧本来就符合松手状态时，无须重画但仍须提交切换，绘制为 0 ms。
跨页面全屏绘制仍约 190–220 ms，不能称作已提高面板刷新率或全屏 60 fps。
另将 PSRAM 行写入明确为对齐 32 位 store，避免依赖 ROM memcpy 的访问宽度；
这一项本身未测得明显全屏提速，不能把局部重绘收益归给它。

最终观察曾出现一个 5 秒窗口仅收到 4099 包、补零 1472 采样，DMA 重启仍为 0，
随后恢复 5000 包/5 秒、补零 0。与收包暂停后原 100 ms 停播判定窗口相符，
但没有主机侧时间戳证据确认停顿来源，保留该异常，不将其误报为全程零补零。
用户确认当时一直连续播放；随后明确要求暂不继续排查该停顿，先提交本轮修改。
本次未加入新的 USB 端点诊断或针对该停顿的试验性修复。
