# 复合固件框架梳理（2026-10-31）

后续分步共存实验见 [显示与无线验证记录](COEXIST_VERIFY.md)。

本文为当前实现审查与后续调整方案，不表示已完成重构。
框架梳理阶段板上使用 `display_core1` demo；随后按用户要求烧录了下述统一日志版。

## 已验证范围与故障边界

- `wifi_ble`：主核运行 ESP-Hosted/embassy-net，Wi-Fi 连续三轮扫描成功，Windows
  实际收到 BLE 广播。
- `display_core1`：主核先初始化 PSRAM，副核初始化显示并持续绘图；用户确认
  移动方块正常，无条纹或闪烁，主核心跳和副核帧数持续增长。
- `desktop`：复合 USB 枚举成功，副核执行到显示初始化及触摸探测完成；用户
  反馈纯红屏，之后没有持续通信。尚未证明日志、PSRAM、中断或跨核锁中的哪项
  是根因，独立 demo 成功不能证明这些功能组合后没有时序与资源问题。

## 当前实现

主核在一个 Embassy executor 中运行时间驱动、USB/音频/键盘/VIA/保存 futures
以及 C5 无线任务。副核运行 `desktop_ui::run`，负责 PSRAM 初始化、MIPI/VDMA、
触摸、UI 和宏按键处理，使用局部 `block_on` 等待异步 VSYNC。
ES8311 在主核配置后，I2C1 转移给副核。共享 `Shared` 在跨核临界区内访问，
同时包含视图、Wi-Fi 命令、键位配置和键盘报告队列。

与已验证的刷屏 demo 相比，集成版本同时改变了 PSRAM 初始化所在核心和并发
时机、VSYNC 等待方式、触摸访问、跨核状态访问，并增加 I2S/USB/SDIO 工作负载。
因此不能仅凭最后一行日志的位置确定阻塞点。

## 串口日志审查

`Cargo.toml` 对 esp-println 0.18.0 关闭默认 features，仅启用 esp32p4、uart、
log-04。`cargo tree -e features -i esp-println` 确认没有启用 critical-section。
本地依赖源码中 `esp_println::with` 在缺少该 feature 时直接执行回调，不取得
跨核锁；log 门面最终也调用同一个 println/UART 路径。

所以当前两个核心确实可能并发写同一串口，日志可能交错。UART 路径逐字节调用
ROM 发送函数并等待 FIFO 空位，日志输出也会占用调用核心的时间。
这是一项应修正的并发设计问题，但还没有证明它导致红屏或整机停顿。当前配置
没有启用 esp-println 自身的锁，因此不能直接称其为“日志锁死锁”；ROM 路径的
并发行为亦未通过本次源码检查证明安全或不安全。

## 建议的职责与资源归属

| 资源/功能 | 所有者 | 其他核心如何使用 |
| --- | --- | --- |
| PSRAM 配置 | 主核启动阶段，一次性完成 | 初始化完成后再启动副核 |
| 双缓冲显存、MIPI、VDMA、显示中断 | 副核 | 主核只发布视图数据，不写显存 |
| GT911、运行期 I2C1 | 副核 | 音频若需运行期 codec 配置，发送请求给所有者 |
| USB 控制器、HID/VIA、UAC1 | 主核 | 副核发送按键事件，读取 USB 状态 |
| I2S/DMA 与音频缓冲 | 主核 | UI 只发送控制命令，不接触样本缓冲 |
| C5 SDIO、Wi-Fi、BLE、网络栈、校时 | 主核 | 副核发扫描/连接请求，接收结果 |
| 键位配置与持久化 | 主核 | 副核使用带版本的配置快照 |
| 正常运行串口输出 | 主核统一发送 | 副核通过有界非阻塞队列提交事件 |

不把所有数据都塞入一个全局锁。最新状态（时间/IP/连接状态）允许覆盖；
扫描/连接请求使用有界命令队列并明确忙状态；按键释放不可静默丢弃，需要
溢出后的全释放/状态重同步策略。ISR 只确认中断、更新计数或唤醒任务。

日志队列满时丢低优先级日志并累计丢弃数，不阻塞副核刷新；不持有业务锁打印，
不在显示/音频 ISR 中同步打印。直接开启 esp-println critical-section 可串行化
输出，但不能替代上述结构：长日志持锁及屏蔽中断可能干扰实时任务。panic/异常
输出单独设计，不能依赖已经停止调度的正常日志任务。

## 启动及逐步集成顺序

1. 主核初始化系统、日志、PSRAM 与静态缓冲，读取持久配置；配置 ES8311 后
   移交 I2C1，或在副核启动阶段由 I2C1 所有者执行 codec 配置。
2. 启动副核显示，收到 ready 和持续帧计数后，建立状态快照与命令通道。
3. 加入已验证的 Wi-Fi/BLE，观察刷新、主核心跳、SDIO 与广播同时持续工作。
4. 加入 USB HID/VIA，再加入 UAC1/I2S；每一步分别验证枚举、输入和音频。
5. 最后接回触摸交互、页面和配置保存。Flash 写入需明确双核停驻及恢复协议，
   并验证停驻期间显示 DMA 描述符维护的影响，不能只确认写入成功。

各阶段记录 ready、帧数、超时与音频欠载计数。对日志假设先做单核统一输出的
对照实验；不要同时改日志、PSRAM 初始化和显示时序后将结果归因于其中一项。

## 统一主核日志对照实验

2026-10-31 已实施 `src/diagnostics.rs`：32 条、每条最多 256 字节的静态队列，
通过 CAS 尝试取得队列所有权，不等待竞争者；竞争或队列满时丢日志并计数。
格式化和 UART 输出均不在队列锁内。`desktop` 在启动副核前注册 logger，
主核 Embassy 任务消费队列；每输出一条日志让出执行权。
日志前缀 ProCpu/AppCpu 标识产生日志的核心，实际 UART 输出都在主核。
面板及 USB Audio 回调的直接打印也改为此路径；其他独立例程未启用队列时
保留原来的直接输出行为。未改 PSRAM 初始化位置、显示参数或业务任务结构。

编译通过：desktop、display_core1、usb_audio。desktop 镜像 2,488,816 字节，
已从 COM6 烧录并自动启动。观察到 USB configured=true、副核显示初始化、
GT911 探测、shared snapshot ready、render complete 和 committed。
同时出现一次 TX DMA underrun/restarting 日志，随后没有后续日志；VIA 只读
探测没有返回，已中止探测。用户确认屏幕仍为纯红。

结论：统一 UART 输出未修复故障，不能将双核直接打印视为已证实的根因。
首次 commit 已返回，但无法仅凭最后日志断定卡在 VSYNC，也不能排除主核停止
调度后队列中仍有未输出记录。当前 panic/异常同样入队：若主核已经不能调度，
日志不能送出，因此“没有异常日志”不代表没有 CPU 异常。
